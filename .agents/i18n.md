# I18n

- Add server and JavaScript keys only under `source/i18n/SC`, `TC`, and `EN`.
- Site names, navigation names, online-role titles, and forum names are JSON objects keyed by `SC`, `TC`, and `EN`; use `i18n::localizeValue()` rather than branching on the locale.
- Store manual `common_secquestion.question` values as JSON maps keyed by those locale names.
- Rebuild language/template caches after changing rendered keys.

## Resolution order

`{lang key}` is substituted when a template is **compiled**, and the value comes from whichever pack wins this merge (`source/class/class_template.php:279-315`):

1. `lang('template')` — the global pack, `source/i18n/{LANG}/lang_template.php`. Always the base, for every module.
2. `lang($path.'template')` — the module pack, e.g. `tag/lang_template.php`. Overrides the global pack.
3. `lang('touch/template')` — added only when `IN_MOBILE`.
4. The style overlay, `template/{tpldir}/i18n/{LANG}/lang_template.php`. Merged **last**, so it wins.

`i18n::getLang()` (`source/class/class_i18n.php:127-144`) applies the same precedence at runtime via `getStyleLang()`, and memoises per file in a `static $loaded`. That is what lets a style-local key resolve in PHP code, not just in templates.

Consequences:

- **Key names are scoped to their pack, not global.** The same name may hold different values in different modules: `no_content` is `没有相关内容` in `tag/`, `暂时没有内容` in `forum/`, and `抱歉，此模块没有更多内容` in `portal/`. `{lang no_content}` in a tag template and in a portal template resolve to different strings, correctly. Never assume a key name is unique — grep the specific pack.
- **Style overlays are one flat file per style+language** (`template/{tpldir}/i18n/{LANG}/lang_template.php`) and are injected into *every* module context. A style key is therefore globally visible inside that style. Give them a style prefix (`x5_*`, `blog_*`) so they cannot shadow core keys.
- **Only the files in step 1 are global.** A key added to a module pack is invisible to other modules.

## After changing a key

- `{lang …}` is expanded at **compile** time, so run `cleartemplatecache()` (a `{lang …}` token surviving into `data/template/*.tpl.php` means the cache is stale).
- The `lang` files themselves are read from disk per request; `loadcache('lang')` only applies when `i18n_custom` is configured. No cache clear is needed for the values themselves — only for templates.
- Rebuild styles with `.agents/tools/rebuild_styles.php` if you also touched a CSS token.

## Conventions

- **Do not pack multiple words into one key.** A translator cannot reorder them, and CJK and Latin need different spacing. Split into fragments and join with `{lang sp}` — `sp` is a space in `EN` and empty in `SC`/`TC`, so one template serves all three. Precedent: `blog_no`/`blog_related`/`blog_content`, `x5_*`, and `tag_no`/`tag_related`/`tag_content`, all replacing earlier combined `*_no_related_content` / `no_content` keys.
- Keep the footer language-switcher `<option>` endonyms hardcoded — deliberate, not an oversight.
- Reuse an existing core key rather than adding a style-prefixed duplicate. `diy_settings` and `load_more` were promoted to the global pack for exactly this reason; they are used from `common/` and `cell/`, so the global pack is the only place both can see them.
- Watch for near-duplicate keys that are actually distinct: `post_newthread` (button label, `forum/lang_template.php`) and `title_newthread_post` (page `<title>`, `lang_core.php`, reached via `lang('core', …)` at `source/app/forum/module/post.php:349`) are unrelated despite the similar names.

## Verifying

Check the **compiled** output, not the source — `{lang …}` becomes a literal there:

```sh
grep -rl 'DIY settings' data/template/     # substituted correctly
grep -rl 'x5_diy_settings' data/template/ # stale cache, not a missing key
```
